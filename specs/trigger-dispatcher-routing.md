# 触发器分发器路由（Trigger Dispatcher Routing）

- 日期：2026-11-25
- 状态：**已实现（同日落地；端到端目验待办）**
- 裁决方式：用户与 agent 设计收敛（2026-11-25 会话，三轮定稿）
- 正身修订关系：**部分修订 `docs/trigger-system.md` 裁决摘要第 7 条**（"同 key 事件投向同一会话、已裁决不做 per-event 会话模式"）——`dispatcher` 档下处理会话即 per-topic 会话；`direct` 档保留旧语义供存量与简单场景。正身文档的条目标注随实现批次同步补加。

## 1. 背景与动机

当前触发器模型（正身 `docs/trigger-system.md`）：一 key 一绑定会话，事件直接投进绑定会话**就地处理**。问题：

1. **上下文干扰**：一个触发器（或组）的事件流往往涉及多个不同任务/话题，全在绑定会话里处理，话题上下文互相混杂、互相污染；
2. **上下文冗余**：处理过程全部留在绑定会话上下文里，后续每轮输入重复背负全部历史 token；
3. **职责混杂**：同一个会话既做"事件归类判断"又做"具体处理"，无法按职能分别配置思考级别与工具面。

本裁决把触发器绑定会话的定位改为**分发器（dispatcher）**：只做话题聚类分箱，不做具体处理。事件由分发器判断"开新会话还是续用某个活跃会话"后，由机制层把**原始事件内容**（不经分发器转述）投递到目标会话。处理会话的上下文按话题纯净隔离；分发器会话可用最低思考档，多任务场景总 token 下降。

## 2. 术语与角色

| 术语           | 定义                                                                                                                                                      |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **分发器会话** | 触发器 key 绑定的会话（`trigger:<id>` / `trigger-group:<gid>`，绑定关系不变）。角色 = 话题聚类分箱，不做业务处理。身份 = 订阅 agent（触发器创建者）本人。 |
| **处理会话**   | 实际处理事件的会话，**恒为创建者本人的会话**（新开或续用）。`creation_origin=trigger`，归属创建者名下（沿用现有归属规则）。                               |
| **事件 id**    | 机制层在事件进入批次时生成的稳定标识（`evt-*`）。分发器按 id 引用标记，事件内容不进工具参数。                                                             |
| **引用式标记** | 分发器的路由输出形态：只声明"哪些事件 → 哪个目标"，不复制、不转述事件内容。                                                                               |

## 3. 裁决摘要

1. **分发器只路由给创建者自己**：触发器由某 agent 创建、仅该 agent 订阅；分发器的路由目标**只有一种**——创建者本人的新会话或活跃老会话。不存在唤醒其他 worker 的情况（worker 创建的触发器同理，处理会话即该 worker 自己的会话，不违反"worker 之间不直连"）。机制层按会话身份**强制校验**路由目标（越权标记拒绝/降级，与"模型传入 owner 一律忽略"同一哲学），不依赖模型自觉。
2. **不做路由表文件**：路由状态（活跃话题 → sessionId 映射）的**唯一事实源是分发器会话上下文**。压缩即话题淘汰——这是设计机制，不是缺陷兜底。依据：(a) 早期路由记录对应的认知会随后续事件修改项目内容而脱节，本就不该长期保留；(b) 时间局部性假设——同话题事件倾向于时间上靠近，能留在上下文里的近期记录大概率仍活跃；(c) 个别跨压缩周期的话题被误淘汰，代价仅为"开新会话重载状态"，处理会话的知识在其状态文件里（"文件是跨会话唯一可信状态"原则兜底）。
3. **压缩提示词契约**：分发器会话使用**特制压缩提示词**（复用 T1/T2 机制与现有压缩实现，仅提示词变体）：只保留近期未完结话题的记录（sessionId + 一句话话题描述 + 近期事件要点），已完结话题淘汰；**sessionId 等精确标识符必须逐字保留，禁止摘要改写**（抄错一个字符即路由失效）。
4. **保守倾向**：分发器判断准则——**不确定是否同话题时开新会话**。宁可多开会话，不可把两个话题混进一个流（混流的上下文污染代价远大于多开的 token 代价）。写进分发器说明注入。
5. **引用式标记，内容不过分发器的手**：分发器用标记工具按事件 id 声明路由；机制层把**原始事件负载**直接投递到目标会话。事件内容不在工具参数中出现（避免上下文与工具参数双份冗余，杜绝转述失真）。**分发器路由不走 ContactAgent**——ContactAgent 是内容传递模型，标记工具是引用标记模型，两者并存、语义不同。
6. **处理会话不回流**：处理会话完成事件后**不向分发器汇报**，结果走状态文件/任务系统。分发器唯一的再输入是后续新事件的再路由。否则分发器退化成聚合中心，上下文干扰问题原样回归。
7. **路由策略三档**（触发器/组配置字段 `routing`）：见第 4 节。
8. **降级与兜底由机制层承担**（见 6.4）：地址失效静默降级新会话、漏标记保守降级、轮次失败留桶重试、连续失败复用熔断。
9. **分发器会话工具面收窄**：只给标记工具与必要只读工具，不给写盘/执行类工具——分发器无业务职能，收窄既是防误用也是安全边界。
10. **UI 标注分发角色**：触发器文件夹条目显示"分发"徽章；处理会话散布在创建者名下（普通会话投影），"谁在干什么"比旧模型清晰。

## 4. 路由策略（`routing` 字段，三档）

| 档位         | 行为                                                                             | LLM 参与           | 适用                                            |
| ------------ | -------------------------------------------------------------------------------- | ------------------ | ----------------------------------------------- |
| `direct`     | 现行为：一 key 一绑定会话，事件直投绑定会话就地处理（正身第 7 条语义原样）       | 处理即该会话       | 存量触发器（缺省，零迁移）、单话题低频触发器    |
| `fixed`      | 规则直投：每个事件批次按固定规则**开创建者新会话**投递，分发器会话不创建、不唤醒 | 零                 | 通知型触发器（每事件独立处置，无话题连续性）    |
| `dispatcher` | 本 spec 主体：事件进分发器会话，LLM 聚类分箱后标记路由                           | 每批次一次分发轮次 | 多话题/多源（尤其触发器组）、话题需连续性的场景 |

- **新建触发器缺省 `dispatcher`**（本裁决的目的形态）；**存量触发器保持 `direct`**（行为突变需用户/agent 显式切换，切换时机留给开发与用户商定，见第 11 节）。
- `fixed` 是廉价通道：平凡策略不该烧 token；`dispatcher` 只在需要语义判断时出场。
- 组订阅（`trigger-group:<gid>`）下分发器会话归属沿用现有组绑定会话归属规则，路由目标恒为该归属 agent 自己。**多源混批拆流是 dispatcher 档的最大受益场景**：旧模型下组内多源事件挤在一个绑定会话必然互扰，分发器按语义拆到各自话题会话。

## 5. 分发器会话语义

### 5.1 生命周期与输入

- 长寿命续用会话（懒创建、同 key 续用，与现有一致）；上下文靠 T1/T2 压缩兜底。
- 输入 = 事件批次（沿用 3s 去抖合并、批上限 50；分发器忙时新事件留 per-session 桶、空闲合并投递——全部复用现有管线）。每个事件带机制层生成的稳定 `evt-*` id。
- 说明注入：README 注入照旧（新会话创建与压缩后重建时）；分发器变体额外注入**分发职责说明**（保守倾向准则、标记工具用法、"不做处理只做路由"）。

### 5.2 分发轮次

分发器轮次的输入是事件批次、输出是标记工具调用（可能多次/批量）。轮次内不产出业务内容。轮次异常计入触发器熔断计数（连续 3 次异常 → error-paused + 通知，现有机制）。

### 5.3 压缩即淘汰

见裁决摘要第 2、3 条。压缩对分发器不是风险而是**话题生命周期管理机制**：过期路由记录被自然清理，活跃话题记录（未完结话题的 sessionId + 话题摘要）被保留带入新上下文。

## 6. 机制层契约

### 6.1 事件 id

事件进入批次时由机制层生成稳定 id（格式 `evt-<…>`，实现定稿）。id 随事件呈现给分发器（批次消息内联，如行前缀），标记按 id 引用。id 在批次内唯一即可，不要求全局持久（事件不跨批次引用）。

### 6.2 标记工具（提案名 `RouteEvents`，命名实现可调）

```
RouteEvents(routes: Array<{
  eventIds: string[]                  // 本批次内的事件 id
  target: { new: true } | { sessionId: string }
}>)
```

- 调用即标记，不携带事件内容；机制层在**分发器轮次结束后**统一兑现标记（读取本轮全部标记，按 target 拆批投递），而非逐调用即时投递——同一 target 的多段标记可合并投递。
- `target.sessionId` 必须是**创建者本人**的会话（机制层按会话身份强制校验）：非本人会话 = 越权，按 6.4 降级处理并记审计。

### 6.3 拆批投递

- 标记兑现 = 按目标拆批：`new` → 以创建者身份 `createTask`（`creation_origin=trigger`，README 说明注入照常），`sessionId` → 投递进该会话（忙则入 per-session 桶合并投递，现有机制）。
- 处理会话的事件输入带 `<system-status>`：`sender=trigger` + `triggerId`（沿用），可选附 `viaDispatcherSessionId`（处理会话可追溯事件途经，便于写状态文件；不构成回流通路）。
- 投递的事件内容 = **原始事件负载**，机制层直传，无 LLM 转述环节。

### 6.4 降级与兜底矩阵

| 情形                             | 处理                                                                           | 审计                           |
| -------------------------------- | ------------------------------------------------------------------------------ | ------------------------------ |
| 标记的 `sessionId` 不存在/已终结 | 静默降级为 `new`（"话题静默淘汰"的运行时另一半：压缩事前淘汰，降级事后兜残址） | `route.degraded`               |
| 越权标记（目标非创建者会话）     | 同上降级为 `new`                                                               | `route.degraded`（记越权详情） |
| 轮次成功但部分事件漏标记         | 按**保守倾向降级**：漏标事件开 `new` 直投（宁可多开不可丢失/混流）             | `route.fallback`               |
| 分发器轮次失败（LLM 错误/超时）  | 事件**留桶**，整批重试分发器轮次（不直投——直投等于把路由决策交给零判断）       | 照常记异常                     |
| 连续轮次失败                     | 计入熔断（3 次 → error-paused + 通知），现有机制                               | 现有熔断记录                   |
| `fixed` 档直投                   | 机制层规则开新会话，零 LLM                                                     | `route.fixed`                  |

> "静默降级"不是掩盖缺陷的兜底分支，而是话题生命周期语义的组成部分——**设计的一部分**，与压缩淘汰共同构成闭环。

### 6.5 审计

路由决策全部入现有 JSONL 审计日志（`<id>/log/audit.jsonl`）：`route.marked`（批次 → 目标 + 事件 id 列表）、`route.degraded`、`route.fallback`、`route.fixed`。误判混流由此可发现、可追溯。

## 7. 会话与 UI 投影

- 处理会话 = 创建者的普通会话（worker 订阅 → worker 名下投影；master 订阅 → master 名下），与现有触发器创建的会话同构，无新投影形态。
  **投影修正（2026-11-25 实测裁决）**：现有侧栏投影（grouped-view `isTriggerSessionTask`）把**所有**触发器来源会话从智能体列表过滤（2026-11-19"触发器文件夹独占承载"裁决），fixed 的多开新会话与 dispatcher 处理会话因此在 UI 上完全不可达。修订：独占承载只对**绑定会话**成立（引擎 sessionBindings 值集）；非绑定的处理会话回归订阅者名下会话列表。归属侧补齐 syncer 准入——非 worker 的触发器来源会话自动准入主智能体组（worker 会话已有 worker 组准入），绑定会话同样准入（组内不可见成员，可见性归 UI 过滤）。
- 触发器文件夹条目：`dispatcher` 档显示"分发"徽章（`direct`/`fixed` 不显示或显示对应档位）；点击条目切换到分发器会话（照旧：首次触发懒创建）。
- 分发器会话本身即普通会话 UI（群聊形态）：用户可旁观——内容是事件批次进、标记调用出，可读、可插话（用户插话走现有协同机制，插话内容进入分发器上下文，分发器可据此调整后续路由）。
- 分发器会话在 UI 上很"薄"（全是事件与标记，无业务产出）——徽章即解释，避免用户困惑"这个会话怎么不干活"。

## 8. 验收场景（MVP）

1. `dispatcher` 触发器首个事件 → 分发器标记 `{new}` → 创建者名下出现新会话 A，**事件原文**出现在 A、不在标记工具参数中；分发器上下文无业务处理内容。
2. 同话题第二个事件（时间邻近）→ 分发器标记续 A → 事件原文投进 A，A 上下文连续。
3. 混批：一批含两个不相关话题的事件 → 批量标记拆两路（一路 `new`、一路续既有会话），互不串扰。
4. 压缩淘汰：话题完结 + 若干压缩周期后同模式事件再至 → 分发器按新话题开新会话（旧 sessionId 已不在上下文）；处理会话从自身状态文件恢复认知。
5. 残址降级：分发器标记一个已终结的 sessionId（可构造）→ 机制层降级 `new` + `route.degraded` 审计，事件不丢。
6. 越权拒绝：分发器标记非创建者会话 → 降级 `new` + 审计记越权。
7. 轮次失败：构造分发器轮次异常 → 事件留桶重试；连续 3 次 → error-paused + 通知。
8. `fixed` 档：事件到达零 LLM 轮次，每批次直投创建者新会话；分发器会话不存在。
9. `direct` 档存量触发器行为与升级前完全一致。
10. 不回流：处理会话完成处理 → 分发器上下文不出现任何处理结果内容。
11. `worker` 身份订阅：worker 创建的 dispatcher 触发器，处理会话全部落在该 worker 名下，不触碰其他 worker。

## 9. 非目标（本轮明确不做）

- 路由表文件 / 路由状态落盘（裁决：压缩即淘汰，见裁决摘要 2）
- 跨智能体路由（分发器只路由给创建者自己；多 agent 分发属未来扩展）
- 处理结果回流分发器 / 分发器汇总报告
- 复杂规则路由（`fixed` 仅"每批次新会话"一种平凡策略；条件路由属未来扩展）
- 处理会话间直连（沟通规则不变：一切经 master）
- 浏览器轮询来源（引擎托管浏览器，另行待办，与本 spec 无关）
