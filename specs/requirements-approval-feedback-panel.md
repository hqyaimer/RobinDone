## 1. 背景与目标

RobinRun 是多智能体协作 Harness，当前人机协作的一切状态都活在会话上下文里：会话一多、上下文一滚动，事项就难以追溯。本功能在软件内置一个后台面板，把三类管理原语从"对话"升级为"状态机"：

| 原语         | 方向                 | 语义                                                                    |
| ------------ | -------------------- | ----------------------------------------------------------------------- |
| **需求 REQ** | 用户 → master        | 工作单："我要这件事被做"。用户已拍板，无需审批                          |
| **审批 APP** | master → 用户        | 决策门："这个方向/优化建议尝试"。非阻塞决策项，区别于会话中的阻塞式询问 |
| **反馈 FBK** | 任何人/智能体 → 系统 | 观察记录："这里可以更好"。经 master 分诊                                |

目标：列表清晰、可跟踪可回溯；新事件自动唤醒对应智能体，形成完整运营闭环。

## 2. 对象与状态机

编号规则建议：类型前缀 + 全局递增序号，如 `REQ-0001`、`APP-0001`、`FBK-0001`（细节格式开发可调）。

MVP 状态集（刻意最小化，后续阶段再扩展）：

| 对象 | MVP 状态流转               | 说明                                                                              |
| ---- | -------------------------- | --------------------------------------------------------------------------------- |
| REQ  | `已提交 → 处理中 → 已处置` | 处置结果为四选一：**受理** / **拒绝** / **挂起** / **转审批**；处置需留结果与备注 |
| APP  | `待审 → 已批准 / 已驳回`   | 驳回理由可选填写                                                                  |
| FBK  | `已提交 → 已处理`          | MVP 中"处理"= master 改状态并可选备注；升格链接是后续阶段功能                     |

数据表建议预留 `links`（JSON，可空）字段用于未来的关联追溯，但 MVP 不做升格/链接的 UI 与逻辑。

## 3. 事件与唤醒语义（本功能的核心）

三类事件（命名仅建议）：`requirement.created`、`approval.decided`、`feedback.created`。

**3.1 强制订阅（系统级保护；2026-11-24 用户裁决修订订阅面）**

- master 对面板事件默认订阅，且该订阅**不可被任何智能体停用或删除**（master 和 worker 尝试操作必须被系统拒绝）
- 订阅面（2026-11-24 修订）：`approval.decided`（用户决策，master 不在场）+ `feedback.created`（worker 反馈）；`requirement.created` 退出订阅面——需求由用户对话转述、master 代录（录入方在场免唤醒）
- 实现约束：订阅的 owner 必须是系统/项目本身，而非任何智能体；这是触发器系统需要支持的首个"系统特权订阅"，属于平台级保证，不是约定俗成

**3.2 串行队列与"处置即释放"**

- master 的唤醒是**串行**的：同一时刻只处理一条，上一条处置完成后才唤醒下一条，不合并
- **"处置完成" ≠ "开发完成"**：指 master 已对该条做出状态决定（REQ 四选一处置 / FBK 改状态）。受理的进入正常开发排期，排期不占唤醒队列——否则一个大需求会堵死整个队列
- `approval.decided`（用户批准/驳回）同样经此队列唤醒 master 去执行
- `approval.created` **不**唤醒 master（见 3.3 作者豁免；master 起草时即已知）
- 面板显示待处理队列（MVP 简单列表即可）

**3.3 作者豁免（防自唤醒环）**

- 作者不因自己创建的条目被唤醒：master 写审批/反馈不唤醒 master；worker 写反馈只唤醒 master、不唤醒作者自己。规则约束对象是智能体（用户提交正常触发对 master 的唤醒）

**3.4 唤醒投递位置**

- ~~建议：事件投递到 **master 的主项目会话**（用户可旁观、可插话），不落到隐藏的触发器会话。实现形态可由开发与用户商定~~
- **裁决（2026-11-24 实测后修订）**：面板 = 数据面，主智能体 = 处理方，**系统订阅是两者唯一通道**。唤醒按标准触发器会话模型投递——`trigger:trg-ops-panel` 一 key 一绑定会话（绑定解析/写回/持久化与普通触发器同一套，触发器文件夹即面板事件的处理台账）。串行（上一条处置完成才唤醒下一条）与不合并仍由面板服务的唤醒队列保证；master 主会话不被运营事件冲刷。

## 4. 权限矩阵（worker 可见性控制是 MVP 必含项；2026-11-24 用户裁决"对话代录"修订）

| 动作                 | 用户（UI）               | master（工具）                                | worker（工具）                           |
| -------------------- | ------------------------ | --------------------------------------------- | ---------------------------------------- |
| 提需求               | ❌（表单退役：对话转述） | ✅ **代录**（author=user，recordedBy=master） | ❌                                       |
| 提审批               | ❌                       | ✅（author=master）                           | ❌                                       |
| 提反馈               | ❌（表单退役：对话转述） | ✅ 代录（author=user）或自录（author=master） | ✅ 自录（author=worker:<id>）            |
| 读需求/审批/全部反馈 | ✅                       | ✅                                            | **仅自己提交的条目**（完整生命周期可见） |
| 改状态/分诊          | ❌                       | ✅                                            | ❌                                       |
| 批准/驳回审批        | ✅                       | ❌                                            | ❌                                       |

- **录入与来源拆分（2026-11-24 裁决）**：`author`=来源（user / master / worker:<id>），`recordedBy`=经手录入者。用户直接告诉 master 需求和反馈，由 master 代录（author=user + recordedBy=master，面板显示代录角标）——对话是录入主界面，面板是账本与决策门
- master 录入的条目一律免自唤醒（录入方在场）：豁免是**通用机制**——系统订阅配置按事件声明 `exemptRecordedBy`（录入者词表），逻辑读配置不写死；requirement.created 退出订阅面
- worker 可见性必须在**数据/接口层过滤**实现，不是 UI 层隐藏（按 author 过滤，语义不变）
- worker 提交反馈需要一条 worker 可用的提交通道（工具/接口形态由开发定）
- 层级纪律不变：worker 的一切诉求经"反馈"入口向上走，master 分诊后才可能变成需求（转用户）或审批

## 5. 数据模型（概念级，不指定实现）

三张表，字段建议：`id`（编号）、`title`、`body`、`author`（user / master / worker:workerId）、`status`、`created_at`、`updated_at`、处置相关字段（结果、备注、时间）、`links`（JSON，预留）。基础审计字段保留即可，无需复杂事件日志表。

持久化要求：队列状态与条目状态落库（沿用现有 SQLite），**重启后不丢**。

## 6. UI（最简）

- 软件内置面板：需求/审批/反馈三个列表 + 条目详情；操作能力按第 4 节权限矩阵
- **2026-11-25 增补**：面板增设第一 tab"进度"（追加式项目里程碑台账，master 独占维护、无事件面、用户纯只读），正身 `specs/progress-ledger.md`——本节"三个列表"由该 spec 扩展为四个 tab
- 关键澄清：**面板 UI 的主要使用者是用户**（提需求、批审批、看全部）；master/worker 是智能体，通过工具接口操作同一份数据
- MVP 不要求视觉打磨，能清晰展示列表、状态、队列即可

## 7. MVP 验收标准（2026-11-24"对话代录"裁决后修订 1/2/4）

1. 用户在**对话里**告诉 master 一条需求 → master 代录（author=user，面板出现该条并带代录角标，不产生唤醒）→ master 处置 → 状态与处置记录在面板可查
2. **串行性**：队列中出现 2 条待唤醒项（worker 反馈 / 审批决定），第 1 条处置完成前第 2 条不唤醒 master
3. master 起草审批 → 面板出现待审批项 → 用户批准 → master 被唤醒执行；驳回同理
4. **录入豁免（原"作者豁免"修订为通用机制）**：master 录入的一切条目（起草审批 / 代录需求 / 代录或自录反馈）不产生唤醒——豁免规则随订阅配置声明（`exemptRecordedBy`），逻辑读配置
5. worker（可用运营专员实测）提交反馈 → master 被唤醒分诊
6. **worker 可见性**：worker 的读取接口只能看到自己提交的条目，看不到他人条目
7. **订阅保护**：master / worker 尝试停用或删除该订阅被系统拒绝
8. 重启软件后，队列与全部条目状态持久不丢

## 8. 非目标（本轮明确不做）

- 升格与追溯链（FBK→REQ→APP 链接）的逻辑与 UI（仅预留 `links` 字段）
- 反馈批量分诊、优先级队列等唤醒优化
- 导出快照、统计视图
- 与邮件通知、任务系统的打通
- 挂起项自动复查触发器

## 10. 与现有系统的关系

- 复用现有 SQLite 与触发器基础设施；"系统特权订阅"是触发器系统的新能力，需平台层支持，属于架构决策，应落 ADR
